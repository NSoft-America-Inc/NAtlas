# 작업지시서 하나 = GitHub 이슈 하나 — 코드 변경 이유를 언제든 역추적한다

## 1. 화면 정의 및 레이아웃 (Layout Specification)

- **레이아웃 구조**: 역추적 체인을 오른쪽에서 왼쪽으로 거슬러 올라가는 **Traceability Chain Layout**. "코드 → 커밋 → 이슈 → order.md"의 4단계 연결이 화면 중앙을 가로지릅니다.
- **비주얼 및 컴포넌트 구성**:
  - **중앙 체인 (좌→우 역순으로 연결)**:
    - `코드 한 줄` ←→ `git commit #abc1234` ←→ `GitHub Issue #42` ←→ `order.md (왜 만들었는가)`
    - 각 노드가 화살표로 연결되고, 클릭하면 다음으로 이동하는 구조 시뮬레이션
  - **하단 시나리오 배지**:
    - "이 코드 왜 이렇게 됐어?" → Issue #42 → order.md → "결제 모듈 성능 문제 때문에 리팩토링함"
  - **우측 혜택 리스트**: "변경 범위가 명확", "이유가 추적됨", "감사/리뷰가 쉬움"
  - **상단 원칙 한 줄**: "작업 1개 = 이슈 1개 = order.md 1개 = 관련 코드 변경 전부가 하나로 묶인다"

## 2. 실질적 본문 내용 (Exact Slide Content)

### "이 코드 왜 이렇게 바뀌었어?" — 지금은 이 질문에 얼마나 빨리 답할 수 있습니까

NStack에서 작업지시서(order.md) 하나는 반드시 GitHub 이슈 하나와 연결됩니다.

**이것이 만들어내는 추적 체인**:

```
코드가 변경된 이유가 궁금할 때 →
  git blame으로 커밋을 찾고 →
  커밋 메시지의 이슈 번호로 이동하고 →
  이슈에 연결된 order.md를 열면 →
  "왜 이 작업을 했는가"가 바로 나온다
```

**이 구조가 주는 장점**:

- **변경 범위가 명확합니다**: 이슈 하나에 연결된 커밋들이 그 작업의 전부입니다. 어떤 파일이 왜 바뀌었는지, 무엇은 의도적으로 건드리지 않았는지 알 수 있습니다.
- **이유가 남습니다**: 6개월 뒤에 "왜 이렇게 만들었지?"라는 질문이 생겨도, 이슈 번호 하나로 당시의 판단과 맥락을 바로 볼 수 있습니다.
- **코드 리뷰가 쉬워집니다**: 리뷰어가 코드만 보는 게 아니라 작업 배경을 함께 볼 수 있습니다.
- **장애 대응이 빨라집니다**: 문제가 생겼을 때, 해당 코드를 마지막으로 바꾼 작업의 order.md를 보면 변경 의도와 주의사항이 있습니다.

**핵심**: AI가 짠 코드라도, 왜 그렇게 짰는지의 이유가 이슈와 함께 영구적으로 연결됩니다.

## 3. 스피치 노트 (Aside Speaker Notes)

_"NStack에서 작업지시서 하나는 반드시 GitHub 이슈 하나와 연결됩니다. 이게 왜 중요한가? 나중에 '이 코드 왜 이렇게 됐어?'라는 질문이 생겼을 때 git blame으로 커밋을 찾고, 커밋에 적힌 이슈 번호로 가면, order.md에 당시 판단과 맥락이 있습니다. AI가 코드를 아무리 빠르게 만들어도, 왜 그렇게 만들었는지의 이유가 이슈와 함께 추적됩니다. 이것이 NStack의 진짜 힘 중 하나입니다. 코드 변경 이유를 언제든 역추적할 수 있는 팀과 그렇지 못한 팀의 차이는, 6개월 뒤에 극명하게 드러납니다."_
