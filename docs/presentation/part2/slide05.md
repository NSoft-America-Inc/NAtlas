# 나중에 찾을 수 있어야 의미가 있습니다 — 문서의 검색 가능성

## 1. 화면 정의 및 레이아웃 (Layout Specification)

- **레이아웃 구조**: 검색하는 장면과 찾아지는 결과를 대비하는 **Search & Find Layout**. 좌측에 검색 입력창, 우측에 결과 카드가 표시되는 구조.
- **비주얼 및 컴포넌트 구성**:
  - **좌측 검색 시뮬레이션**: 검색창에 "결제 오류 수정"을 입력하는 모습. 실제 검색 인터페이스처럼 보이게.
  - **우측 결과 카드 3개**: "2024-03 결제 모듈 리팩토링", "2024-05 PG사 연동 오류 수정", "2024-08 환불 플로우 개선" — 각각 담당자, 날짜, 핵심 결정 요약 표시.
  - **하단 대비**: "구글 드라이브에서 찾기 ❌ (어디 있었지?)" vs "NStack에서 찾기 ✅ (2초)"
  - **강조 문구**: "잘 쌓인 문서는 필요할 때 3초 만에 찾을 수 있어야 합니다."

## 2. 실질적 본문 내용 (Exact Slide Content)

### 문서가 있어도 찾을 수 없으면 — 없는 것과 같습니다

문서를 쓰는 것만큼 중요한 것이 있습니다: **나중에 필요할 때 찾을 수 있는 것**입니다.

지금 많은 팀이 이런 상황입니다:

- 어딘가에 문서는 있다
- 어디 있는지 모르겠다
- 찾는 것 자체에 시간이 더 든다
- 결국 처음부터 다시 코드를 읽는다

NStack의 3가지 문서는 처음부터 "나중에 찾을 수 있도록" 설계됩니다:

- **프로젝트별로 정리됩니다** — 어느 프로젝트, 어느 작업인지 명확하게
- **날짜와 함께 쌓입니다** — 언제 이 결정을 했는지 바로 확인 가능
- **키워드로 검색됩니다** — "결제 오류"를 치면 관련된 모든 기록이 나옵니다
- **NAtlas가 시각적으로 보여줍니다** — 어떤 작업이 어떤 작업과 연결됐는지 지도로 볼 수 있습니다

**나중에 찾기 쉽도록 처음부터 구조를 잡는 것** — 이것이 NStack 문서 체계의 핵심입니다.

## 3. 스피치 노트 (Aside Speaker Notes)

_"문서를 아무리 잘 써도 나중에 찾을 수 없으면 소용없습니다. NStack의 3가지 문서는 처음부터 검색할 수 있도록 설계됩니다. 프로젝트별로 정리되고, 날짜와 함께 쌓이고, 키워드로 검색할 수 있습니다. '결제 오류' 하면 관련된 모든 기록이 나옵니다. 구글 드라이브에서 파일 이름 기억나지 않는 것을 찾아 헤매는 것과 완전히 다른 경험입니다. NAtlas는 이 문서들을 지식 지도로 시각화해서 보여줍니다. 이건 Part 4에서 직접 보여드리겠습니다."_
