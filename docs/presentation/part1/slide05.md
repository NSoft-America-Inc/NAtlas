# 코드를 처음부터 읽는 것이 인수인계가 된 상황

## 1. 화면 정의 및 레이아웃 (Layout Specification)

- **레이아웃 구조**: 이상과 현실을 명확히 대비하는 **Ideal vs Reality Split Layout**. 좌측은 이상적인 인수인계, 우측은 현실의 인수인계. 같은 항목을 나란히 대비.
- **비주얼 및 컴포넌트 구성**:
  - **좌측 (에메랄드, "이상적인 인수인계")**: 문서 아이콘 + 코드 아이콘 + 맥락/결정 이유 아이콘. 전달 받은 사람이 "이해 완료" 상태.
  - **우측 (회색/로즈, "실제 인수인계")**: 코드 아이콘 하나만. 전달 받은 사람이 "처음부터 읽어야 함" 상태. 소요 시간: "수일~수주".
  - **중앙 구분선 위**: "당신의 팀은 지금 어느 쪽입니까?"
  - **하단 강조 문구**: "AI가 만든 코드가 많아질수록, 이 격차는 더 벌어집니다."

## 2. 실질적 본문 내용 (Exact Slide Content)

### 인수인계란 무엇이어야 하는가 — 그리고 지금 실제로 무슨 일이 벌어지는가

**이상적인 인수인계**:

- 코드 (무엇을 만들었는가)
- 설계 이유 (왜 이렇게 만들었는가)
- 결정 기록 (어떤 대안을 검토했고 왜 이걸 선택했는가)
- 주의사항 (이 부분을 건드릴 때 알아야 할 것)

전달 받은 사람이 이것들을 가지면: **며칠 안에 자리를 잡을 수 있습니다.**

**실제 인수인계**:

- 레포지토리 주소
- "이 사람한테 물어봐" (퇴사했거나, 기억 못하거나)

전달 받은 사람이 해야 하는 일: **코드를 처음부터 읽으며 의도를 추측합니다. 수일에서 수주.**

---

AI가 만든 코드가 많아질수록 이 문제는 더 심해집니다. 작성 속도가 빠를수록, 이유를 남길 여유는 더 없어집니다. 악순환입니다.

## 3. 스피치 노트 (Aside Speaker Notes)

_"인수인계를 받아보신 분, 또는 해보신 분 계십니까? 이상적인 인수인계는 코드뿐 아니라 왜 이런 구조를 선택했는지, 어떤 고민이 있었는지를 함께 전달하는 겁니다. 그런데 현실에서는 레포지토리 주소 하나로 끝나는 경우가 많습니다. 받은 사람은 코드를 처음부터 읽으면서 의도를 추측해야 합니다. AI 시대에도 이 문제는 해결되지 않았습니다. 오히려 AI로 코드를 빠르게 많이 만들수록 이 문제는 더 심해집니다. 만드는 속도와 기록의 속도가 맞지 않으니까요."_
