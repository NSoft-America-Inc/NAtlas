# Slide 4: 현업의 실상 - 사내 솔루션의 '문서화 부재'와 애로사항

## 1. 화면 정의 및 레이아웃 (Layout Specification)

- **레이아웃 구조**: 좌측에는 실제 개발 도구 화면을 직관적으로 재현한 **VS Code IDE 파일 Explorer 및 터미널 윈도우 (IDE Explorer Split Terminal)**, 우측에는 상세 기술 명세 텍스트 컬럼 배치. 화면 2열 전체를 촘촘한 코딩 창과 빽빽한 분석 리스트로 꽉 채워 설계합니다.
- **비주얼 및 컴포넌트 구성**:
  - **좌측 IDE 창**: 윈도우 컨트롤러 3색 버튼 및 다크 코딩 에디터 질감 구현.
  - **사이드바**: 파일 트리 구조 묘사 (`src/App.tsx`, `store.ts` 등은 정상 노출되나, `docs/` 폴더 옆에는 붉은색 경고 `[X]` 마크와 함께 2년 전 마지막 수정되어 먼지 쌓인 잿빛 `README.md` 표현).
  - **우측 에디터**: README.md 내용에 FastAPI 포트 18420 바인딩 충돌 시 왜 18420이 선택되었는지 근거 설명이 전무하여, 개발자가 슬랙에 질문을 던지라는 경고 및 크리티컬 에러 로그 박스가 붉은 네온 보더로 입체 출력됨.

## 2. 실질적 본문 내용 (Exact Slide Content)

### ⚠️ 인수인계서와 설정 근거 누락으로 마비되는 사내 솔루션 유지보수

대다수의 사내 핵심 개발 솔루션(어드민 관리 도구, 전사 자동 배포기, 스키마 툴, 권한 관리 어드민 등)은 릴리즈 기능 위주로 고속 팽창되어 왔으나, 정작 이를 유지보수하고 확장하는 데 필요한 **"Why(의사결정 맥락)"**가 기재되어 있지 않습니다. 이로 인해 개발팀은 매번 유지보수 마일스톤 때마다 아래와 같은 심각한 생산성 장애를 마주합니다.

- **🚫 설정값 근거의 원천 부재 [18420 포트의 미스터리]**: 
  - 로컬 구동 시 백엔드 포트를 왜 `18420`으로 지정했는지, 왜 `source_mode`를 `local`과 `remote` 이중화 구조로 설계했는지에 대한 설명이docs 폴더에 전무합니다. 
  - 포트 충돌이나 옵션값 파손 발생 시, 원천 기획 의도를 알 수 없어 트러블슈팅 공수가 무한정 지연됩니다.
- **🔄 슬랙 검색 구걸 루프의 악순환 [오리지널 개발자 의존]**: 
  - 장애 원인을 규명하기 위해 docs 폴더를 뒤지지만, 텅 비어있거나 2년 전 템플릿 README만 남겨져 있습니다. 
  - 결국 과거 슬랙 채널을 2~3시간씩 허망하게 뒤지거나, 타 파트로 전환 배치되었거나 휴가 중인 오리지널 개발자에게 다이렉트 메시지(DM)를 보내 답을 구걸해야 하는 **"조직적 비효율"**에 상시 노출됩니다.

## 3. 스피치 노트 (Aside Speaker Notes)

*"솔직히 가슴 아프지만 우리 현업의 현실을 말씀드려 보겠습니다. 현재 우리 사내 솔루션들 중 상당수는 변경 히스토리와 수정 맥락이 문서화되어 있지 않습니다. 실제 IDE 저장소 폴더 구조를 보면, 핵심 비즈니스 로직이 담긴 src 폴더는 잘 돌아가지만, 아키텍처 의사결정을 밝혀줄 docs 폴더는 비어있거나 2년 전 방치된 오래된 리드미만 잿빛으로 누워있습니다. 결국 FastAPI 사이드카가 포트 18420번을 두고 충돌이 나거나 에러가 터졌을 때, 왜 이 값을 골랐는지 알아낼 기술적 근거가 부재하여, 매번 슬랙을 몇 시간씩 뒤지거나 휴가 간 최초 개발자에게 다이렉트 메시지를 보내 답을 구걸해야 하는 심각한 업무 지연을 마주하고 있습니다. 이 기술 무책임의 고리를 끊어내야 합니다."*
